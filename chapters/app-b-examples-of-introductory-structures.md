# Appendix B: Examples of Introductory Structures

> Source: *The Minto Pyramid Principle* by Barbara Minto, OCR pages 235-253.

## Core Idea

Most business introductions use the Situation–Complication–Question structure and lead the reader toward one of four standard questions. The hardest introductory forms become manageable when the writer defines the problem precisely—especially the desired result, R2—before structuring the answer.

## Frameworks Introduced

### Four Standard Questions

Use these questions to identify the introductory pattern and the document’s governing question:

1. **What should we do?**  
   Used for solving a problem, obtaining a desired result, choosing among known alternatives, responding to an audit, or recommending a change to an unquestioned practice.

2. **Should we do what we plan to do?**  
   Used to test whether an action is right, whether implementation will create problems, whether a solution works, or whether it will achieve the objective.

3. **How do/did we do something?**  
   Used to explain execution, implementation, a completed solution, a new activity, system operation, or directions.

4. **Why did it happen?**  
   Used chiefly in progress reviews to report findings after agreed work has been completed.

### Situation–Complication–Question

Use this structure to make the reader’s question arise naturally:

1. State the accepted **Situation**.
2. Introduce the **Complication**—a problem, change, uncertainty, or choice.
3. Identify the resulting **Question**.
4. Make the Key Line answer that question directly.

Its strength is relevance: the introduction supplies only enough shared context to trigger the question answered by the document.

### Proposing Steps to Solve Problems

Use for consulting proposals and project plans, where the solution has not yet been found.

1. Define the client’s problem in the introduction.
2. State that help is wanted.
3. Answer, “How would you go about helping us solve our problem?”
4. Structure the body around the analytical steps.
5. Treat qualifications, timing, staffing, and fees as information outside the core thinking structure.

**Failure mode:** Standard proposal headings encourage overlapping lists. “Introduction,” “Background,” and “Objectives and Scope” all tend to redefine the problem, while “Issues,” “Technical Approach,” and “Work Plan and Deliverables” overlap around the solution process.

### Consulting Proposal Around “Reasons”

Use in a competitive proposal, where the governing question is, “Are you the consultant we should hire?”

Organize the reasons to show that:

1. You understand the problem using the **Situation-R1-R2 structure**.
2. You know how to solve it.
3. You have relevant problem-solving experience.
4. Your business arrangements—timing, staffing, and fees—make sense.

Use a proposal around **“steps”** when confirming work with an established client; use **“reasons”** when selection is competitive. Project plans are always structured around the process.

### Dealing with Alternative Solutions

1. Define R2 clearly.
2. Judge every possible course against R2, not against the other courses.
3. Discuss alternatives in the body only when the reader already recognizes them and asks, “Which one?”
4. If the real choice concerns different outcomes, structure around **alternative R2s**.
5. If unwanted alternatives must be shown, place them in the introduction or an appendix, preferably in a criteria matrix.

**Why it works:** A course should be recommended because it reaches R2—not merely because other courses have weaknesses.

### Describing Changes to Processes

Use **before-after analysis** when recommending process changes:

1. Draw the present process.
2. Mark where problems occur.
3. Draw the required process.
4. Identify the changes needed to move from old to new.
5. Use those changes as the Key Line.
6. Explain only the defective steps beneath the relevant Key Line points.

## Key Concepts

- **Situation:** Context the reader already knows and accepts.
- **Complication:** The development that creates uncertainty or requires action.
- **R1:** The current, unsatisfactory result or starting condition.
- **R2:** The specific desired result against which a solution must be tested.
- **Problem Definition Framework:** A visual mapping of the opening scene, disturbing event, R1, and R2.
- **Key Line:** The major answer points immediately supporting the document’s governing answer.
- **Alternative R2s:** Different desired outcomes, each of which may justify a different action.
- **Process visualization:** Drawing operational steps so that failure points and required changes become visible.
- **Progress review:** An introduction that recalls promised work, states that it was completed, and asks what was found.

## Mental Models

- **Use Situation–Complication–Question when the reader’s governing question must emerge naturally from shared facts.**
- **Think of R2 as the test that distinguishes a solution from a merely plausible action.**
- **Use a steps structure when the reader is buying an approach; use a reasons structure when choosing a provider.**
- **Think of process change as the difference between two pictures: before and after.**

## Anti-patterns

- **Comparing vague alternatives by pros and cons:** This substitutes relative comparison for testing against R2.
- **Introducing options only to reject them:** It burdens the reader without supporting the positive reason for the recommendation.
- **Balancing strengths and weaknesses mechanically:** Exhaustive lists obscure the governing logic.
- **Writing proposals under inherited headings:** Overlap fragments the problem definition and analytical approach.
- **Describing every process step:** The reader needs the failure points and corrective changes, not an operational transcript.
- **Presenting problems without solutions:** Properly stated problems often reveal the required changes.
- **Putting unfamiliar claims into the introduction:** The introduction should rely on information the reader knows or will accept.

## Worked Example

A reporting team inherits responsibility for monthly performance charts.

**Before**

`Divisions → manual/repeated data entry → calculations → graphics system → chart book → presenter changes`

Errors arise during entry, calculation, and unvalidated presenter revisions.

**R1:** Charts are sometimes incorrect or inconsistent.  
**R2:** Reliable charts produced through a controlled process.

**Introduction**

- **S:** The analysis team now produces most chart books used in management presentations.
- **C:** Despite computer processing, errors persist because two inefficient input systems feed the charts.
- **Q:** What changes should be made?

**Key Line answer**

1. Create a direct data link to the corporate computer.
2. Automate graph-point calculations with a reliable routine.
3. Require presenter changes to be revalidated.

The body need explain only how each identified failure occurs and how its corresponding change removes it.

## Key Takeaways

- Identify which of the four standard questions the reader is asking.
- Define R1 and R2 before drafting the introduction.
- Test recommendations against R2 rather than against competing options.
- Match proposal structure to whether the reader is buying a process or selecting a provider.
- Visualize old and new processes before recommending changes.
- Keep the introduction brief; place detailed diagnosis beneath the Key Line.
